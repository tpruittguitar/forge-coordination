# Existing jobs are not discovery work

`job-identity.js` is the shared, read-only matcher for source discovery, the upstream observer, fresh automatic-intake prechecks, and relevance preparation. A uniquely identified canonical master or terminal-archive job is accounted as `PRESENT` and removed from the discovery worksheet/intake backlog. The source alias and its history stay in the ledger. No canonical row is deleted or changed.

Evidence, strongest first:

- A job-identity URL, employer-scoped requisition, scoped ATS posting ID, or compatible claimed primary ID. Conflicting employer, title, worksite, or known requisition makes the result ambiguous.
- Otherwise, one normalized employer/title/city-and-state match. Common title abbreviations (Sr, Jr, Mgr, Dir, VP, SVP, EVP, Mfg, Ops, Asst, Assoc and Dept), neutral trailing company suffixes, explicit former-name annotations, punctuation and case-insensitive US state codes/names and country suffixes are normalized. Parenthetical job shifts and employer divisions remain meaningful. Compatible rows with unknown locations prevent a weak match from being treated as unique.

Indeed `jk` and other identity-bearing URL query parameters are retained. ATS IDs retain provider/board scope. Different LinkedIn/Indeed listing IDs require shared employer requisition or scoped ATS evidence; names/site or a claimed primary ID alone cannot bridge them. Salary comparables and review evidence URLs are not identity proof. Missing, remote, state-only, country-only, multi-city and unparsed locations cannot independently establish a same job. Explicit location-open, regional, national/global and multi-site/facility/plant scope also require stronger posting identity: a board city alone establishes neither presence nor independence. Multiple canonical IDs remain ambiguous. Unknown request outcomes and original Writer fences still require separate reconciliation and must never be replayed or considered complete from job presence.

Discovery reports separate `identity_held_roles` from proven `existing_roles`. Admission previews return `SKIP_EXISTING`/`skipped` for verified existing identities. The automatic path obtains fresh authenticated master and archive snapshots before source fetching; its `existingNoWrite` receipt records the source, canonical ID, basis and row hashes, with zero submissions and no write-completion claim. Relevance preparation similarly closes discovery work and releases only an unfenced helper reservation.

An unresolved original request fences its own posting/requisition and compatible worksite, not every common title at the employer. Full original records retain work mode, operating scope and identity evidence. The observer advances its report-history checkpoint schema to re-read original saved reports once, so earlier projections cannot permanently erase that evidence. Observation timestamps, not history iteration order, select the newest explicit evidence; equally timed contradictions stay unresolved. Supported work-mode and scope fields survive the final Writer-record projection without changing request IDs. The generic title-family fence exemption requires precise single-site locations in different states on both sides, with no shared posting/requisition/primary ID or explicit broad scope. Same-state city labels, metro aliases, unknown locations and grouped duplicates remain protected. Legacy fences without the original record remain conservative. No saved request is replayed or cleared by this classification.

This matcher does not replace Writer receipt/readback/accounting validation. Those exact transaction checks and canonical mutation rules are unchanged.

## Regressions

Run the `Discovery identity regression tests` PR workflow, or the Node test command it declares. The broad local suite additionally covers all source-trial, source-intake, pipeline-observability, intake-drain, live-backlog, manual-backlog and relevance-screen tests. Source-trial integration fixtures use `ENRICH_FC_DIR`; observer fixtures use `ACTIVITY_FC_DIR`. Set `CHROMIUM_PATH` for the installed browser when running the worksheet browser test.

## Batch lookup cost

Load one fresh authenticated master snapshot and one terminal archive per bounded run/batch, then build and reuse one in-memory index. Refresh before acting if the snapshots exceed the freshness contract; never download or rebuild the full population per candidate. Writer-side dedupe remains a final race guard for genuinely new candidates when another process inserts a role after the snapshot. Proven existing discoveries do not need a Writer submission to confirm the match.

`node tools/source-trial/benchmark-identity.js MASTER_FILE ARCHIVE_FILE LEDGER_JSON [NAIVE_LIMIT]` measures local read/parse, index construction and matching without network calls or state mutations. A November 7, 2026 run on 4,964 master rows, 785 archive rows and 670 saved pending candidates took a median 297 ms end-to-end across five measured batches after warm-up: 134 ms read/parse, 148 ms index, and 16 ms to match all candidates. In contrast, deliberately repeating local reads and index construction for 100 candidates took 28.66 seconds. The component medians need not sum to the median total. These are cached local-file measurements, not production network latency or an estimate of a live run's entire duration.
